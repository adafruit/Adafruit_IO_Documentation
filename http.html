    Adafruit IO HTTP API

    The Adafruit IO HTTP API provides access to your Adafruit IO data from any programming language or hardware environment that can speak HTTP. The easiest way to get started is with an Adafruit Learning Guide and a simple Internet of Things capable device like the Feather Huzzah or a more complicated one like the PyPortal.

    API Versions

    Adafruit IO has more than one version of its HTTP API. A request is routed to a version by its path or by its Accept header:

    • v2 is selected by the /api/v2/ path prefix, or by sending Accept: application/vnd.adafruit.io.v2.
    • v1 is selected by the /api/v1/ path prefix, or by sending Accept: application/vnd.adafruit.io.v1.
    • A request with no version in the path or header (for example /api/{username}/feeds) is handled by v1, which is the default.

    v2 is the documented and supported API, and everything in these docs uses it. v1 and unversioned paths still work so older clients keep running, but they are deprecated and are not documented here. Always use https://io.adafruit.com/api/v2/ for new projects.

    Authentication

    Your Adafruit IO Key is used to restrict or grant access to your data. The key is unique and covers every use of the Adafruit IO API for your account. You can access your key on any IO page by clicking on the golden key icon:

    Or by clicking on the "View Adafruit IO Key" link in the small screen drop-down menu while you're visiting Adafruit IO.

    Now you can copy the key directly from the information form that pops up, or copy one of the code samples that includes your key and username together.

    curl -H "X-AIO-Key: b780002b85d6411ca0ad9f9c60195f72" \
    https://io.adafruit.com/api/v2/test_username/feeds

username = "test_username"

    When making HTTP requests to Adafruit IO, you can include the API key as a query parameter named x-aio-key or as a request header named X-AIO-Key. In both cases, "X-AIO-Key" is case insensitive.

    NOTE: if you regenerate your AIO key, your old key will be immediately invalidated, so you'll have to replace it in any scripts or sketches where it is in use.

    NOTE: it is a best practice to avoid including your API key in the URL as a query parameter. Some situations may require this, but try to avoid it if you can.

    Rate Limiting

    Adafruit IO imposes a rate limit on all data modification APIs to prevent excessive load on the service. If a user performs too many data create, update, or delete actions in a short period of time then the system will start rejecting requests.

    If you have a free Adafruit IO Account, the rate limit is 30 data points per minute.

    If you have upgraded to an Adafruit IO Plus account, the base rate limit is 60 data points per minute.

    If you exceed this limit, HTTP requests are rejected with a 429 Too Many Requests response and a notice will be sent to the {username}/throttle MQTT topic. You can subscribe to the topic if you wish to know when the Adafruit IO rate limit has been exceeded for your user account. This limit applies to all Data record modification actions over the HTTP and MQTT APIs, so if you have multiple devices or clients publishing data, be sure to delay their updates enough that the total rate is below your account limit.

    One data record modification is any action that creates, updates, or deletes a single Data record. When you send several records in one request (a group or batch create), each record counts as one action, and if there is not enough room left in your limit the whole request is rejected with 429 and no data is saved.

    A best practice is to only save or modify data within the hot part of your code loop. You want to handle authentication and any other API requests (creating/getting feeds, etc) before you start your main code loop where you save data.

    Repeatedly exceeding limits over MQTT can lead to a temporary ban. See the MQTT Rate Limiting page for details.

    We have general API throttles to ensure the API isn't being improperly used either by accident or for nefarious purposes. This throttle level is higher than any data rate limit throttles, but you may run into it if your code isn't optimized. One example would be if in the main loop of your code you are not only sending data, but also authenticating, retrieving all feeds, or anything else that doesn't involve saving or modifying data to a feed. In that scenario, you would be hitting the API 3x more times than necessary, and could get throttled, even if you're saving data within your allotted rate limit.

    HTTP Request Limits

    Separately from the data rate, each API user (identified by IP address and API key) is limited to 300 HTTP requests per minute across the API. Some endpoints have stricter limits:

    Endpoint Limit
    Feed sharing (/feeds/{feed_key}/shares) and coupon checks 10 requests per minute
    POST to tokens, feedback, and social reports 2 requests per minute per IP address

    Requests over a limit receive a 429 Too Many Requests response. For the overall and per-endpoint request limits the body is plain text (Retry later); for data rate limits it is JSON (see Errors). Wait a minute and retry.

    Plan Limits

    Free IO+
    Feeds 10 Effectively unlimited
    Dashboards 5 Effectively unlimited
    Groups 5 Effectively unlimited
    WipperSnapper devices 2 Effectively unlimited
    Data rate 30 data points per minute 60 data points per minute
    Data storage 30 days 60 days

    IO+ users can purchase boosts for a higher data rate and longer storage.

    Storage is counted from the time data is uploaded, not from a record's created_at value, so records uploaded with a created_at in the past are kept for the full storage period from upload.

    Pagination

    Adafruit IO’s API returns 100 data points by default and at most 1000 at a time. To get more data if your feed is over that many data points, you’ll need to “paginate” the data.

    What does this mean?

    When you perform an HTTP data GET query, the results are sorted newest-to-oldest (see the note on start_time below) and include 5 X-Pagination-* headers and the Link header field in the response. You can see an example of the headers on the right.

    Pagination Headers

    X-Pagination-Count: 250
X-Pagination-Limit: 250
X-Pagination-Total: 83027
X-Pagination-Start:
X-Pagination-End: 2019-05-03T17:35:13.637+0000
Link: <https://io.adafruit.com/api/v2/abachman/feeds/humidity/data?end_time=2019-05-03+17%3A35%3A13+UTC&limit=250>;rel="next", <https://io.adafruit.com/api/v2/abachman/feeds/humidity/data?before=eyJ0aW1lX2lkIjoiMEU1M043N0syUjdUR1Y3MEY3UjJFUVlRVlkiLCJmZWVkX2lkIjoiNjE3MzcwLjAifQ%3D%3D&end_time=2019-05-03+17%3A35%3A13+UTC&limit=250>
    • Count (X-Pagination-Count) is the number of data points in the current request.
    • Limit (X-Pagination-Limit) is the requested limit if it was included as a parameter (at most 1000), otherwise 100.
    • Total (X-Pagination-Total) is the total number of data points in the feed for the given start_time and end_time. Note, this value may be up to 5 minutes behind real time.
    • Start (X-Pagination-Start) is an ISO-8601 formatted date value based on the start_time parameter in the original request, if one was given.
    • End (X-Pagination-End) is an ISO-8601 formatted date value based either on the end_time parameter from the original request or the time when the original request was made.
    • Link is a set of one or more URLs that point you to related resources.

    Whenever Limit and Count are equal and Total is more than Count, that’s evidence that more data is available. That's where the Link (Link) header comes in.

    The Link Header

    For Adafruit IO Link always contains at least one URL inside angle brackets, that's the link to the page of data you are currently looking at. In the example above, the first URL is https://io.adafruit.com/api/v2/abachman/feeds/example.counter-1/data?end_time=2019-05-02+22%3A33%3A22+UTC&limit=250. The first URL given in the Link header can be used to request the same data set again in the future. Even if your original request didn't include any parameters, the Link URL will include an end_time parameter that reflects the time at which you made the request. This is how we can make sure you can request the same data repeatedly.

    The example Link value above also includes a next section: rel="next", <https://io.adafruit.com/api/v2/abachman/feeds/example.counter-1/data?before=eyJ0aW1lX2lkIjoiMEU0V0RWSk1SNlgxNUgxV0FSR0c2SzFIRUgiLCJmZWVkX2lkIjoiNzMuMCJ9&end_time=2019-05-02+22%3A33%3A22+UTC&limit=250>. The rel="next" part is written right after the first URL, but it marks the URL that follows it as the next page of data (standard Link header parsers may not read it this way, so split the header on the comma instead). As long as there is more data available, the Link header will include a rel="next" URL. It updates on each request, so you can page through data by making a request, parsing the Link header to get a next URL, and then using that URL to make another request. If your initial request includes end_time, start_time, or limit parameters, those parameters will be included in the rel="next" URL. Data is sorted by descending created_at date (newest first, oldest last), so the next page of data is the next older page. The exception is a request with start_time but no end_time: it returns the oldest limit records after start_time, so include end_time whenever you paginate.

    When visualized on a timeline, the concept of pagination looks like this:

    Note that long running, frequently updated feeds could have more than a hundred pages of data. In the example above, with a limit of 250 records, it would take 330 requests to get all the data. If you make requests without a small delay in between, you will hit a rate limit. To avoid this, watch for 429 HTTP error responses and handle them in code by adding a 30 second timeout between requests and request the largest size permitted, right now that's 1000 records.

    If your goal is to store and study the data offline, though, you would be better off downloading the whole feed using the Download button built into Adafruit IO on the web.

    Data

    Data is at the heart of Adafruit IO. Everything your device measures and records becomes a data point on an Adafruit IO Feed.

    You can create, read, update, or delete data records. Every CREATE, UPDATE, or DELETE action on a data record counts against your data rate limit (points per minute), which is shared between HTTP and MQTT.

    A data value may be at most 1024 bytes (1 KB) when the feed's history is on, and at most 524288 bytes (512 KB) when history is off. Larger values are rejected with a 422 error.

    Data points belong to feeds, so every Data API call starts with a Feed URL.

    Feeds can be addressed in any {feed_key} position by their key (for example temperature), by their numeric feed ID, or as group_key.feed_key to select a feed within a specific group.

    Data reads default to JSON. Many read endpoints can also return CSV or plain text when the URL ends in .csv or .txt (or the Accept header asks for it). Endpoints that list data (GET .../data and GET .../data/{id}) can return GeoJSON when the request sends Accept: application/geojson (Content-Type: application/geojson also works); the response is an array of GeoJSON Feature objects (or a single Feature for one data point), and an optional callback query parameter wraps the result for JSONP. Records without a location are returned without a geometry.

    Note that there are endpoints for submitting multiple data points to a feed, and multiple feed values to a group, see feeds/{feed_key}/data/batch and groups/{groupname}/data endpoints.

    To get the file, poll the status endpoint. It lists the feed's five most recent downloads. Each entry has a state (building, completed, or error), a progress_percentage, and a url for the file. The url expires after about a minute, so request the status again whenever you need a fresh link.

    Only one download can be requested per feed every 10 minutes. A second request inside that window returns a 429 with an error message, plus these headers:

    Header Description
    X-RateLimit-LimitSeconds the length of the cooldown window, in seconds
    X-RateLimit-Timeout seconds remaining until another download can be requested

    Feeds

    Feeds are the core of the Adafruit IO system. The feed holds metadata about the data you push to Adafruit IO. This includes settings for whether the data is public or private, what license the stored data falls under, and a general description of the data. The feed also contains the sensor data values that get pushed to Adafruit IO from your device.

    You will need to create one feed for each unique source of data you send to Adafruit IO.

    Anywhere a {feed_key} is expected you can use the feed's key (for example temperature), its numeric feed ID, or group_key.feed_key to address the feed within a specific group.

    You can create, read, update, or delete feeds. Creating, updating, and deleting feeds does not count against your data rate limit; only creating, updating, and deleting data does.

    There are also endpoints for submitting multiple data points to a feed, or multiple feed values to a group, see feeds/{feed_key}/data/batch and groups/{groupname}/data endpoints.

    Feeds with visibility set to public can be read by anyone, with or without an X-AIO-Key. This covers the feed itself, its details, and reading its data (data, data/{id}, data/chart, data/last_value, data/retain, data/last). Public reads are subject to the same rate limiting as other requests, see Rate Limiting. Creating, updating or deleting always requires the owner's key. first, next and previous need write access, so they are not available on someone else's public feed.

    GET /{username}/feeds returns the full feed list only when you request your own feeds. If you request another user's feeds, or add public=true to your own, the response contains only public feeds and leaves out owner-only fields such as status, status_notify and status_timeout. Private feeds are never listed or readable by other users, and are reported as not found.

    Public groups work the same way: GET /{username}/groups/{group_key} can be read without a key when the group is public, and GET /{username}/groups?public=true (key required) lists only public groups.

    Feed Sharing

    Share a feed with another Adafruit IO user so they can read it (or read and write it) with their own account and key. Sharing is managed by the feed owner, using the owner's {username} and key. Shares are per feed.

    A share has a level:

    Level Effect
    readable the default. The shared user can read the feed and its data.
    writable the shared user can read the feed and its data, and also write to it.

    A share also has a status: pending (invited, not yet answered), approved, ignored (declined or blocked by the invitee) or cancelled. Access is granted when the invitee approves and revoked if the share is deleted, ignored, or set back to pending.

    Once approved, the shared user addresses the feed through the owner's username, with their own key. For example, over HTTP they can use GET /api/v2/{owner_username}/feeds/{feed_key}/data, and over MQTT they can subscribe to {owner_username}/feeds/{feed_key}. Writes need the writable level. Data sent to a shared feed counts against the owner's data rate (see Rate Limiting).

    Limits and rules:

    • An owner can have at most 10 pending shares. Delete some, or wait for them to be answered.
    • A disabled feed cannot be shared.
    • You cannot share a feed with yourself, with a user who has blocked you, or with someone who has already declined it.
    • A feed can be shared with a given user or email address only once.
    • Requests to /feeds/{feed_key}/shares (list and create) are limited to 10 per minute. See Rate Limiting.

    Dashboard sharing is not available through the API.

    Webhooks

    Webhooks are one way disconnected web services can share data with each other, automatically. For example, say you wanted to get a user’s latest Twitter message. Instead of constantly connecting to the twitter API every minute to check if a new message has been posted, you can ask Twitter to update a webhook URL on each post. That means Twitter will contact you when there’s new data. But, as you can imagine, you need a webserver to listen for that posting. In this case, Adafruit IO can act as that webhook destination.

    Adafruit IO only supports receiving data at this time.

    These data publishing webhook methods do not require authentication. That means you can freely use the URL from a public form without leaking your authentication data.

    You can create new feed webhook receivers by visiting a feed page and using the "Webhooks" link.

    Actions

    Actions let Adafruit IO do something for you when a situation occurs: for example, send an email when a temperature feed goes above a value, publish to another feed every morning, or post to a webhook. An action starts with a trigger (new data arriving on a feed that matches a condition, or a time schedule) and then runs a series of blocks that can read feed values, do logic and math, and send an email, SMS, webhook request, or feed value.

    Actions are built visually with blocks in the Actions editor at io.adafruit.com. Create and edit actions there. The API lets you list, inspect, rename, start/stop, and delete them, and you can also create one by posting an action definition you've copied from an existing action.

    The older Actions API (/{username}/actions and /{username}/triggers) is deprecated and is not documented here. Use /{username}/dynamic_actions.

    The Action Object

    Field Type Description
    id integer the action's id, used in the paths below
    name string the action's name
    description string a description of the action
    run_status string started (the action runs when triggered), stopped (it doesn't), or alerted (it was stopped automatically after 5 failed runs in a row)
    validation_status string invalidated (waiting to be checked), validating, valid, or invalid. Only valid actions run.
    bytecode_validation_errors array reasons the action is invalid, if any
    bytecode object the action's definition (see below)
    schedules array the schedules found in the action's triggers, as cron-style strings
    watched_feeds array feeds whose new data triggers the action
    delay_seconds integer seconds the action waits after being triggered before it runs
    block_count integer number of blocks used, or -1 if the action isn't valid
    heavy_block_count integer number of blocks that send something out (feed value, email, SMS, webhook), or -1 if the action isn't valid
    run_count integer number of times the action has run
    failure_count integer number of consecutive failed runs
    last_run_at string time of the most recent run
    last_run_log string log from recent runs
    last_run_output object output from the most recent run
    last_check_at string time of the most recent trigger check
    last_check_log string log from recent trigger checks
    last_check_output object result of the most recent trigger check
    created_at string creation time
    updated_at string last update time

    The bytecode object is the action's definition, saved by the Actions editor. It has a version, settings, a list of triggers, and a list of expressions (the blocks that run when a trigger fires). It is meant to be written by the editor, so the easiest way to get a valid one is to read it from an action you built there.

    Limits

    • An action can have at most 100 blocks, and at most 20 of them can be "heavy" blocks (set feed value, email, SMS, webhook). Actions over these limits are marked invalid and never run.
    • An action runs at most once every 5 seconds. Triggers that arrive sooner are skipped.
    • A single run is stopped if it takes longer than 10 seconds.
    • After 5 failed runs in a row, the action's run_status becomes alerted and it stops running. Editing its bytecode resets this.
    • The SMS block is limited to 25 messages per day. The email block requires a verified email address.
    • Changing an action's bytecode resets it to stopped if it was alerted, and it must be validated again before it will run.
    • Actions publish and read feed data like any other client, so feed data rate limits still apply. See Rate Limiting.

    Permissions

    Permissions control who can see or change your feeds, groups, and dashboards. By default, everything you create is private. Add a permission to:

    • make a record public, so anyone can read it without an API key, or
    • share a record with one specific user, giving them read or read/write access.

    Only the owner of a record can list or manage its permissions. Requests for another user's records return 404, and permission requests are not allowed from browser (cross-origin) scripts.

    For example, to make the temperature feed public:

    $ curl -X POST -H "X-AIO-Key: {io_key}" -H "Content-Type: application/json" \
  -d '{"permission": {"scope": "public", "mode": "r"}}' \
  https://io.adafruit.com/api/v2/{username}/feeds/temperature/acl

    Scopes and modes

    Scope Meaning
    public Anyone can access the record, signed in or not. Public access is always read-only: write access is never granted, even if w or rw is sent (the response still shows the mode you sent)
    user Shares the record with one other user. scope_value is that user's numeric ID (as a string or number). A user permission takes priority over the record's public permission for that user

    Other scope names (secret, organization, device) are accepted when saving but are not currently enforced, so don't rely on them.

    An empty mode ("") grants nothing. It is the way to keep a permission record in place without giving access. If mode is omitted when creating a permission, no access is granted, so always send r for read access.

    Public permissions and related records

    Making a dashboard public readable also makes every feed on that dashboard that you own public readable (read-only), so the dashboard's blocks can display. Changing or removing the dashboard's permission later does not remove those feed permissions. Feeds on the dashboard that belong to other users are not changed.

    Removing a feed's public permission, or making it unreadable, removes that feed from other users' dashboards where the feed was visible only because it was public. Dashboards of users the feed is explicitly shared with are not affected.

    Services

    Adafruit IO provides a few integrated services that you can use with your AIO key: Weather, Air Quality, Randomizer, Messages (SMS), Time, and an Image Formatter.

    Weather, Air Quality, Randomizer and Messages work by creating an integration record. Once a record exists, Adafruit IO publishes its data to MQTT topics, and you can also read it over HTTP with the endpoints below. These endpoints are for scripts and devices using an AIO key, and requests from other websites (cross-origin browser requests) are rejected.

    IFTTT is set up from the IFTTT service page and the Adafruit IO service on ifttt.com, not through this API. There is no Zapier integration.

    Time

    The Adafruit IO time service does not replace a time-synchronization service like NTP, but it can help you figure out your local time on an Internet of Things device that doesn't have a built in clock. Time is also published on MQTT time topics.

    Unauthenticated Time

    These endpoints don't need an AIO key and return plain text (not JSON), always in UTC.

    HTTP Request

    Response Sample:

    Get Time in Milliseconds

    HTTP Request

    HTTP Request

    GET/api/v2/time/ISO-8601

    Get Time (JSON or Text)

    HTTP Request

    GET/api/v2/utilities/time

    $ curl -H "Accept: application/json" https://io.adafruit.com/api/v2/utilities/time

Request text with Accept: text/plain (or a .txt extension), which returns a single value chosen by the output query parameter: iso8601, rfc822, or, if output is omitted, the millis value. Note that the millis value is Unix time in seconds, not milliseconds. Use /api/v2/time/millis for milliseconds.

    Parameter Type Required Description
    output string false Text responses only: iso8601 or rfc822. Defaults to the millis value.

    Image Formatter

    Downloads an image from a public URL, resizes it, and returns it as a BMP file, which is handy for small displays on microcontrollers. Available on Free and IO+ accounts.

    Limits: the source image can be at most 1 MB and must be at a public http:// or https:// URL (private and internal addresses are rejected). Free accounts can make 1 request per 60 seconds, and IO+ accounts 1 request per 5 seconds. Extra requests get a 429.

    HTTP Request

    GET/api/v2/{username}/integrations/image-formatter

    $ curl -H "X-AIO-Key: {io_key}" -o image.bmp "https://io.adafruit.com/api/v2/{username}/integrations/image-formatter?url=https://example.com/photo.jpg&width=128&height=64&output=BMP16"

    Returns the image (Content-Type: image/bmp). A POST with the same parameters also works. A bad parameter, an image that can't be loaded or is too large returns a 422 with a message.

    Query Parameters

    Parameter Type Required Description
    url string true Public URL of the source image.
    width integer true Output width in pixels. Positive integer.
    height integer true Output height in pixels. Positive integer.
    output string true Bit depth: BMP1, BMP8, BMP16, BMP24 or BMP32.

    Errors

    The Adafruit IO API uses the following error codes:

    Error Code Meaning
    400 Bad Request -- Your request is invalid or was in the wrong format.
    401 Unauthorized -- Your API key is wrong or you're trying to view a resource you don't own.
    403 Forbidden -- This action is not permitted.
    404 Not Found -- The specified record could not be found.
    422 Unprocessable Entity -- You've sent data we can't accept/understand (for example, a missing value field or a failed validation), or you requested a format that we don't serve.
    429 Too Many Requests -- You're sending or requesting data too quickly! Slow down! See Rate Limiting.
    500 Internal Server Error -- We had a problem with our server. Try again later.
    503 Service Unavailable -- We're temporarily offline for maintenance. Please try again later.

    Most validation failures return 422, but some endpoints (such as Actions) return 400 instead, so check for both.

    Error Response Body

    Error responses are JSON, and the error field comes in two forms. Clients should handle both.

    A string, used by most errors:

    {
  "error": "request failed - cannot process request"
}

    An array of messages, used by some create and update failures, along with the status code:

    {
  "error": ["Name can't be blank"],
  "status": 400
}

    A 429 caused by the overall HTTP request limit is plain text (Retry later) rather than JSON.
